# 单会话与 Orchivane 配对试跑

日期：2026-10-20。被测 Skill：0.3.1，源码提交 `a86ba04724b32076625cac9c72033ff1c62d098b`。这是一轮真实原生桌面对话实验，任务是合成的小型回归案例，每题每组只跑一次。

**本轮没有观察到协调请求减少。** 两组各完成三题，额外协调请求均为零；Orchivane 组记录更完整，但累计执行时长与 token 用量更高。不能据此证明技能节省用户时间，也不能证明两种方式普遍等效。

English: Both workflows completed all three small synthetic tasks with zero extra coordination requests. Orchivane used more cumulative active time and reported tokens overall. No specialist chat was created. This pilot does not establish a human-time saving or the value of persistent multi-chat collaboration.

## 任务、预算与实际执行

| 题目 | 相同业务要求 | 每组轮次上限 | 单会话实际 / Orchivane 实际 |
| --- | --- | --- | --- |
| S1 小修改 | 名称去空白、小写、过滤空值，保留顺序与重复；CLI 和 README 一致 | 4 | 1 / 1 |
| S2 跨产物变更 | 先实现库存汇总，再追加 BOM、状态过滤及校验顺序；代码、CLI、README、契约同步 | 4；每阶段最多 2 | 2 / 2 |
| S3 接班与重复请求 | A1 执行一次；全新会话从文件接班完成 R2/A2；完全相同请求再次投递，不能重复 apply | 4；准备 1、接班最多 2、重复 1 | 3 / 3 |

共六个 trial、八个新原生聊天、十二个执行轮次，无额外补跑。Orchivane 可自行选择单会话或最多一个专业协作者，实际三题都没有创建专业会话。S3 两组各有准备者和全新接班者，旧会话停止，不读取其转录；这是同样施加的接班边界，不是并行协作。

每个“轮次”是一次原生聊天派发至该轮完成，包含其内部工具调用。所有参与者合并计数。原生创建工具不能硬性限制 token，因此实现的是**相同轮次预算上限，不是相同实际 token 或金额**。没有用剩余额度追求更好结果。评测方准备夹具、机械投递阶段消息、收集日志与评分是两组共用的测量开销，不计作用户节省的时间。

运行前冻结 [protocol.md](protocol.md)、[plan.json](plan.json)、起点摘要、顺序和评分器。[frozen-manifest.json](frozen-manifest.json) 保留原摘要；其中 `grader/grade.py`、`grader/calibration.json` 在公开包中分别为 `grade.py`、`calibration.json`，字节不变。相同起点逐文件核对，两组均使用 `gpt-6.1-sol`、`high`，从每个实验会话的模型上下文记录确认。Skill 在全部 trial 中不变。

起跑顺序按固定种子生成：S1、S2 先单会话，S3 先 Orchivane，组间允许重叠执行。协议称其为 balanced randomized，但实际是三题的 2:1 顺序，未做到严格等量；缓存、调度和负载也未控制，不能把时差直接归因为技能。

Orchivane 的 S3 留下入口、职责索引和分阶段交接包，当前记录明确替代 A1 的待接班描述；单会话保留一份普通 `HANDOFF.md` 及实际收据，两者都能继续工作。这说明本题额外结构带来了记录成本，但无法确定它在更长项目中是否会回本。

### 指标如何读

- **协调请求**：要求用户搬运已有信息、重复已给约束、处理职责冲突或重新批准已授权动作的次数。原始任务、计划内变更、接班、重复投递及普通进度不算。两组也没有额外澄清、人工介入或要求用户作新判断。
- **人工时间**：未测量，记为 `null`。这里只审阅了脚本化试验中的请求行为；没有真人计时、认知负担问卷或多位独立标注者。零请求不是“人工成本为零”。
- **时长**：原生工具报告的每轮 `durationMs` 之和，S3 加上旧、新两个聊天；包含该轮内部工具等待，不含阶段间评测方操作。不是整个实验墙钟耗时或用户等待时间。
- **命令数**：原生 `commandExecution` 项的数量，一项可能包含多个 shell 操作。文件编辑工具批次另列于 [metrics.json](metrics.json)，不把命令数误称全部工具调用数。
- **token**：每个聊天最终 `total_token_usage` 只取一次，S3 两个聊天相加，避免累计计数重复相加。输入含多次模型请求的系统、技能与工具上下文，且大量输入命中缓存；不是独立文本长度。`output_tokens` 两组合计 12,655 / 18,709；缓存、输入及 reasoning 分项在原始指标中，reasoning 不再次加到 total。
- **费用**：缺少完整计费数据，所有 `cost` 为 `null`。不把 token 总数或审计工具对空集合的 `sum: 0` 解释成美元或免费。
- **关键违规**：检查了轮次、协作者、跨题/评分器读取、旧会话转录、网络/归档/调度及受保护文件修改，未观察到违例；这是已读取轨迹的范围，不是操作系统级沙箱证明。

## 失败、修正及局限

两组 S2 都先写新增测试、让旧实现失败，再在同一轮内修改并通过；保留各一项非零命令记录，不能当成额外 trial，也不能从最终结果中抹去。Orchivane S3 准备阶段一次读取尚不存在的索引文件返回非零，随后正常准备，没有向用户求助或试验补跑。

原生测量阶段，控制方有两次未送达 solver 的工具编排错误：一次 JavaScript 语法错误、一次读取回执的长度参数超限。纠正后重新执行测量操作，没有追加 solver 轮次或修改业务输入，属于测量设施开销。打包检查另有一次把 ignored Python 字节码当文本读取而失败，按公开文件范围排除缓存后核验通过，未改变 trial。原始回执、真实聊天 ID 和本机路径留在私有记录；公开包只含脱敏消息、指标及产物。

本轮不足以证明用户想要的长期协作收益，原因具体如下：

1. 单会话基线已经零请求，主指标存在地板效应；三题都短、说明充分，没有独立长期角色的上下文积累。S2 实际只测试跨文件一致性，**没有形成跨职责协作压力**。
2. Orchivane 实际没建专业会话，因此没有测到总控读取多个角色交付、解决职责冲突的节省。这不是“多会话比单会话快”的实验。
3. 两组都是同一默认模型及同一宿主，但其他插件未全局禁用，单会话仍看得到 Orchivane 的描述。S1 单会话实际读了 Superpowers 入口和 Ponytail；O 组读固定 Orchivane。提示词还有明确的协作规则差异，所以比较的是完整工作方式，不是仅替换 Skill 文件的严格消融。
4. S3 的新会话创建、阶段输入替换和投递由共同评测方负责；接班边界保留了文件，未制造真实崩溃、并发写入、丢失记录或归档。不能把评测方代办的操作宣传成 Orchivane 的自主节省。
5. 只有每题一对，未随机重复、未校准真人协调标注；不能做显著性、生产成功率、普遍优劣或等效推断。

固定功能评分器对组名不作判断且未给 solver 阅读；人工轨迹审阅者知道组别，因此并非全流程盲评。运行前用五个正确、三个错误样本校验功能评分器；这不等于人类协调成本裁判已校准。它只适用于受信任的本题 Python 产物、S1/S2/S3 及 phase 1/2，不是任意提交的安全执行器。调用会导入候选代码；不要用它执行不可信项目。

## 复现与公开证据

- [inputs.json](inputs.json)：逐文件初始内容，经 [initial-hashes.json](initial-hashes.json) 核验；[changes.json](changes.json) 为阶段变更。
- [prompts.json](prompts.json)：实际派发文本，仅将试验目录、固定技能目录和私人授权引用替换为占位符；S3 重复请求与首次接班文本完全一致。
- [artifacts.json](artifacts.json)：终态业务文件及接班记录，保留 `.runtime/` 数据；不含 Git、临时缓存、solver 自写测试或重复的题目文件。[artifact-hashes.json](artifact-hashes.json) 对应公开脱敏后的字节。
- [checkpoints.json](checkpoints.json)、[trace-evidence.json](trace-evidence.json)：所有评分检查点、逐轮可见助手消息、协调标注与重复前后摘要一致性；无隐藏推理和原始聊天导出。
- [results.jsonl](results.jsonl)、[metrics.json](metrics.json)：六个正式结果、字段定义对应上述口径。`agent_version` 包含组别、提示版本及共同模型设置；Skill 固定 0.3.1。
- [audit.json](audit.json)：benchmark-copilot 的离线记录审计：六条计划记录齐全，无重复/缺失/版本问题；`release_approval=false`。它只审数据契约，不重新判定轨迹或证明效能。

离线复核（无模型调用、无创建聊天）：

```sh
.venv/bin/python -m unittest discover -s tests -p 'test_paired_evidence.py' -v
```

该检查重建临时目录，复核冻结摘要、六个终态，并确认错误规范化、旧契约和重复执行能被评分器拒绝。它是运行后可复现检查，不冒充新增原生 trial 或运行前校准。

重新运行原生实验须先取得创建/派发授权，使用全新隔离目录和对话：

1. 从 `inputs.json` 为每题每组落盘同样文件。S3 先以 `{"label":"baseline"}` 提交 `report.py`、配置与 `.gitignore`，再写回提供的 `keep-local-change` 配置，使其成为未提交修改。
2. 从上述源码提交完整冻结 `skills/orchivane/`。将 prompts 中占位符替换为本轮真实路径和人类授权出处；题目目录和 Skill 可读，评分器、另一组和历史 trial 不可读。
3. 按 `order.json` 派初始任务。S2 两组首阶段完成并保存快照后写入同一 `CHANGE.md`，再发变更提示。
4. S3 准备完成、保存快照后，将实际输入替换为 R2：表头 `item,quantity`，三行 `pen,2`、`book,3`、`map,4`；写入 `RESUME.md`，用完全全新的会话接班，不能 fork 旧历史。
5. 接班完成后保存实际运行文件摘要，向同一接班聊天重复**完全相同**的提示。到阶段完成或预算停止，不提供外部评分结果或修复提示。
6. 结束后读取实际产物和完整可见轨迹，按协议评分并保留所有失败。使用 `python3 tests/paired/grade.py S3 <trial-root>` 等固定任务入口；S2、S3 首阶段加 `--phase 1`。评分结果看 JSON 的 `passed`，不能只看进程退出码。

## 本轮决定

保持 Skill 0.3.1，不因未证明收益而继续添加规则、角色或运行时。README 与价值判断同步补充这项无增益结果。小任务继续优先单会话。

若继续验证，先选一个已有真实协调负担、需要长期角色积累的脱敏工作流，预先记录用户搬运次数与实际分钟数，再做独立重复；两组保持相同业务验收和预算，不强行创建角色来制造差异。本轮不自动追加这批实验。
