# 隔离接班与异常恢复实验

日期：2026-10-20。测试对象：从提交 `33fb0c4` 冻结的完整 Orchivane 0.3.1。实验中的数据、源码与角色均为专用夹具，没有操作产品项目。

## 预先确定的范围

总控加三个新建原生桌面对话：旧实施主责、干净的接班主责、独立验收。最多创建3个聊天、派发10轮任务，至多一轮规则修订与针对性复测；每个业务尝试跨消息最多一次apply。没有另购API调用、联网研究、后台轮询、自动化或归档。模型沿用宿主默认设置，其他已安装技能可能参与；不是隔离的因果实验。

旧主责执行 T1/A1（R1输入，2行合计5），随后停写。接班目标执行 T1/A2（R2输入，3行合计9）。源码仓库有一个需保留的未提交配置，必需输入在Git忽略的 `.runtime/` 下。工具每次apply都会追加日志，**自身没有去重**；因此重复副作用可以通过日志条数识别。只读运行不会创建结果或日志。

原生聊天实际读取冻结入口和必要模块，控制方保存原生命令、完整输出及回执。公开内容是脱敏实验摘要，真实聊天ID、原始对话和本机路径仅保留本地。Skill快照7项摘要均经核验；不是自动发现测试。

## 已观察到的过程

| 阶段 | 输入或动作 | 观察 |
| --- | --- | --- |
| 旧主责交付 | R1，累计一次apply | 结果为5，审计一条；停写并说明ignored输入和未提交配置 |
| 首次接班 | 新目录漏掉ignored输入，同时保留R1结果 | 实际只读运行报缺失文件；拒绝接班，没有自行复制或执行apply，未将R1认作A2完成 |
| 恢复依赖 | 总控从独立备份复制R2并核摘要 | 实际运行得到9，源码与未提交配置保留 |
| 主责冲突 | 注入active/stopped相互矛盾的记录 | 接班者保留阻塞，未凭运行成功切换职责；这是记录故障注入，没有真实旧进程并发写入 |
| 正式接班 | 总控消除注入冲突，接班者再次只读验收 | 验收后总控切换唯一主责；新主责实际执行A2，结果9、日志一条 |
| 重复投递 | 完全相同任务文本再次发送；另放入历史A1回执副本 | 接班者复用A2证据，没有再执行脚本；8项受保护内容摘要一致，日志仍一条 |

重复任务包含跨消息一次的明确预算，接班者仍保有上一轮上下文和持久回执。不能将本例推广为失忆、回执丢失、并发重复投递或事务级exactly-once保证。历史A1与R2版本判断有实际证据；“延迟回执”通过文件副本注入，没有模拟消息服务乱序或网络超时。

## 记录收口问题

A2执行后，总控交接入口仍把A2 apply列为首个未完成任务；重复投递时接班者识别了这个冲突，未重复执行。原始入口与重复投递前的摘要已保留。它是控制方现行记录未同步的问题，不能把副作用检查通过写成整个协作过程没有问题。

独立初审确认H1–H6在限定场景内有通过证据，但因两项记录问题拒绝整体收口：交接入口的A2待办未更新（R-C1），角色表仍标接班者“待接班”（R-C2）。总控保留原文件快照，只修现行入口，将A2标为已执行、技术已验、一次额度已用尽，并同步接班状态；业务文件没有改变。修正后的独立复核结论见下方最终结果。

另发现两次测量错误，均保留失败而非隐去：接班者首次重复核验把证据副本中的日志也相加，误得两次执行；随后改为核对真实运行目录，确认仍是一条，没有补跑业务。验收者首次将“重复投递轮内8项未变”套到后来已登记验收者的现场，也触发断言；逐项核查后确认是合法的角色登记更新。**副本不算新增执行，历史摘要只约束其对应时间窗口。** 本报告采用真实执行目录的结果，并区分重复投递窗口与后续控制记录修正。

初审认为现有Skill已经明确要求同步现行入口，没有证据支持增加规则或更改版本。因此本轮优化验收材料与复现步骤，修正控制记录，保留Skill、插件清单和安装缓存0.3.1，不新增去重运行时。

最终结果：**独立针对性复核通过，R-C1/R-C2关闭；六项限定行为检查与本轮记录收口完成。** 复核再次确认实际A2日志一条、业务内容未变。总控随后将“待复核”更新为“已复核”，所有原生测试会话保留空闲，没有归档。控制方记录共创建3个聊天、派发8轮（旧主责1、接班者5、独立验收2），没有用剩余上限补跑。复核核对了3份创建回执，但没有独立审计账户全局调用量；计数不等于成本测量。

独立验收读到六个接收方执行轮次的39个命令记录和六次回执变更，保存的输出未截断；控制方的全部复制、切换及原始授权过程未完整收录在该证据包。可核的是恢复前后文件、备份摘要、接班与执行顺序及实际创建回执，不宣称独立审计覆盖了控制方每一步。测试环境为macOS本地Codex桌面，业务夹具使用Python3.9.6；未单独记录桌面构建号或模型ID。

仓库静态校验及18项离线测试通过，其中2项为新增夹具检查。远端CI以本次提交的Actions结果为准。已更新README、兼容性、研究/价值判断、验证记录与贡献指南；技能、插件清单、历史案例与安装缓存无需变更。归档、自动化及跨平台能力仍无法由本轮核验。

## 复现材料与步骤

夹具位于 [fixtures/recovery](fixtures/recovery/report.py)：标准库脚本、基线配置、[R1](fixtures/recovery/r1.csv)与[R2](fixtures/recovery/r2.csv)。新增的[离线测试](test_recovery_fixture.py)只验证夹具：缺输入失败、恢复后只读不写入，以及重复apply确实留下两条日志；这些测试不测模型决策，也不创建原生聊天。

在仓库外准备隔离目录，复制脚本和配置，初始化小型Git仓库并提交基线；加入 `.runtime/` 忽略规则后，将配置标签改为 `uncommitted-handoff-value`，保持未提交。各阶段保存输入、结果与控制记录快照。

1. 将R1复制为旧目录 `.runtime/input.csv`，原生旧主责执行 `python3 -B report.py --attempt T1/A1 --apply` 一次，交付并停写。
2. 独立保全源文件、未提交配置、ignored输入和审计；复制新工作目录时故意遗漏 `.runtime/`，保留历史结果。交接包说明当前输入是R2，先让新原生接班者只读核验。
3. 总控恢复R2输入并核摘要；在主责记录中注入明确标记的active/stopped冲突，要求只读重验。保留失败回执后，由总控收口冲突，再次验收。
4. 通过后切换唯一主责，派发 T1/A2，允许一次apply并要求实际结果和日志验收。保存已执行状态和证据；若刻意保留旧待办做故障注入，单独声明，不能把这种矛盾留作现行入口。
5. 冻结结果、日志、输入、源码、配置和主责记录摘要，重复投递**同一任务与同一尝试**，不增加预算。检查日志没有新增、受保护内容未变化；恢复执行不得只看消息到达顺序。
6. 独立验收读取命令记录与真实文件，区分业务执行、技术检查、接班切换和最终验收。同步现行记录后再次核验收口；冻结原失败材料。

未来复现必须重新获得原生创建与消息操作授权，沿用明确上限和停止条件。不要在CI里自动执行该流程。归档后恢复、创建返回丢失、真实双写、调度转接、跨客户端和效率收益均不在本次验证范围。
